## 3. 회원 마이그레이션

### 테이블 매핑
`xe_member` → `rx_member` 컬럼은 완전히 동일(`member_srl`, `user_id`, `password`, `email_address`, `user_name`, `nick_name`, `regdate`, `last_login`, `is_admin`, `denied` 등). 그대로 복사 가능.

### 비밀번호 — 예상보다 훨씬 유리함
`password` 컬럼 값을 703건 전수 확인한 결과:
- **486건(69%)**: `sha256:{iterations}:{salt}:{hash}` 형식 (XE의 PBKDF2 저장 포맷)
- **217건(31%)**: 옛날 raw hash (평문 md5/sha1류로 추정, 길이만으로 32/40/16자 등 다양)

Rhymix의 `Rhymix\Framework\Password` 클래스를 직접 열어 확인한 결과, **`pbkdf2` 알고리즘 시그니처(`/^[a-z0-9]+:[0-9]+:/`)가 XE의 `sha256:N:salt:hash` 포맷과 정확히 일치**함. 즉:
- `MemberModel::isValidPassword()`가 로그인 시 이 포맷을 자동 인식해서 검증하고, **성공하면 그 자리에서 자동으로 bcrypt로 재해싱해서 저장**하는 로직이 코어에 이미 있음(`member.model.php:1347-1377`, `password_hashing_auto_upgrade` 설정이 기본 켜짐).
- 따라서 **486명은 `password` 컬럼 값을 그대로 복사하기만 하면, 비밀번호를 몰라도 기존 비밀번호로 로그인 가능** — 강제 초기화 불필요.
- 나머지 217명(raw hash)은 XE가 실제로 어떤 알고리즘으로 생성했는지 코드 확인 없이는 100% 장담 못 함. Rhymix가 길이 기반으로 md5/sha1을 추정 시도하긴 하지만, 검증되지 않은 위험 구간이므로 **이 217명은 로그인 실패 시 "비밀번호 재설정" 안내로 자연스럽게 유도**하는 게 안전(강제 일괄 초기화보다 나음 — 어차피 성공하는 사람은 그냥 로그인되므로).

→ **결론: 비밀번호는 원본 값을 그대로 복사, 별도 변환 로직 불필요.** 배포 후 "비밀번호가 안 되면 재설정해주세요" 공지 한 줄이면 충분.

### 커스텀 필드
`extra_vars`가 PHP 직렬화 문자열(`O:8:"stdClass":...`)로 저장되어 있고, 필드가 가입 시기별로 다름(오래된 계정은 `home_address`/`home_tel`/`msn`, 최근 계정은 `notation`(기수)/`phone`(배열)/`address`). `unserialize()`로 풀어서 새 사이트가 실제로 쓰는 필드(**기수** `notation`, **연락처** `phone`)만 추출하고 나머지(`msn`, `home_tel` 등 죽은 필드)는 버리는 정규화 로직이 필요함.

## 4. 게시글/댓글 마이그레이션

`xe_documents`/`xe_comments` → `rx_documents`/`rx_comments`: 컬럼이 거의 동일(2번 표에서 확인한 이관 대상 게시판만). 신경 쓸 부분:
- `module_srl`은 새 게시판의 module_srl로 치환 (예: notice의 132 → 신규 news 게시판의 실제 module_srl)
- `document_srl`/`comment_srl`은 **원본 값 그대로 재사용**(2026-08-20 확정). 작성자·첨부파일 참조 무결성을 그대로 유지할 수 있고, 원본 값이 이미 신규 사이트에서 만든 테스트/데모 데이터의 srl 범위(백 단위)보다 훨씬 큰 값(수만 단위)이라 충돌 가능성 낮음. 다만 실행 직전에 신규 사이트 시퀀스 테이블(`rx_sequence`)을 이 최댓값 이상으로 맞춰야 함(안 그러면 마이그레이션 이후 신규 작성 글의 채번이 기존 값과 충돌)
- `status`(PUBLIC/SECRET 등), `comment_status` 값은 그대로 호환됨
- `extra_vars`는 이관 대상 게시판에는 사실상 없음(8건 전부 schedule 게시판 것)이라 신경 쓸 필요 없음

## 5. 첨부파일 마이그레이션

`xe_files`(6,609건, 이관 대상 게시판분은 이 중 일부만) → `rx_files`. 컬럼은 거의 동일하되:
- 경로 형식이 다름: 구버전은 `./files/attach/{images|binaries}/{module_srl}/{upload_target_srl}/{hash}`, Rhymix는 날짜 기반(`./files/attach/images/{yyyy}/{mm}/{dd}/{hash}`) 구조를 씀
- **재작명(날짜별 재배치) 대신 원본 디렉터리 구조를 그대로 복사**하는 걸 권장 — `files/attach/legacy/{module_srl}/{upload_target_srl}/...`처럼 별도 하위 폴더에 원본 트리를 그대로 두고, `uploaded_filename` 컬럼에 그 경로를 그대로 기록. 10GB를 새 명명 규칙에 맞게 재배치할 이유가 없음(다운로드 URL은 `file_srl` 기준으로 나가지 실제 경로를 노출하지 않음)
- `mime_type`, `width`, `height` 등 신규 컬럼은 비워도 동작에 지장 없음(값이 필요한 시점—썸네일 생성 등—에 Rhymix가 파일을 열어 재계산하는 경로가 있는지는 실제 이관 시 샘플로 검증 필요)
- **첨부파일 원본 자체(`xe/files/attach/`, ~10GB)는 이 워크스페이스에 없음** — NAS에서 별도로 확보해야 실행 가능한 단계 (기존 remaining-work.md 5번 항목)

### 6-1. 일정 게시판 → 캘린더 (수동 권장)
`xe_document_extra_keys`를 확인해보니 옛 `schedule` 게시판(module_srl=299)에 실제로 "일정시작/일정종료/반복주기" 등 구조화된 필드가 설정돼 있었음 — 처음엔 완전 비구조 텍스트일 거라 예상했는데 아니었음. 다만 실제 값이 채워진 문서는 **10건 중 1건뿐**(`document_srl=300`)이고 나머지 9건은 이 폼을 안 쓰고 그냥 글만 썼음. 건수가 너무 적어 자동 변환 스크립트를 짜는 비용이 안 나옴 — **admin이 캘린더 관리자 화면(이미 구현됨)에서 10건을 직접 입력하는 걸 권장**.

new-site-ia.md에 이미 "과거 축제게시판 데이터는 별도 아카이브로 우선 보관, 추후 이관 검토"로 명시돼 있어 이번 스크립트 범위에서 제외. 524건의 원본 게시글에는 새 작품전시회의 고정 양식(작품명/작품사진/간단설명/제안서)에 대응하는 구조가 없어서(자유 텍스트 게시글), 나중에 이관하기로 하면 사람이 골라서 재입력하는 방식이 될 가능성이 높음.

### 6-3. 과제게시판 → homework 모듈 (보류)
새 과제게시판은 과제(`homework_task`)와 제출물(`homework_submission`)이 분리된 구조인데, 옛 `assignment` 게시판(1,094건)은 출제글과 제출글이 구분 없이 같은 게시판에 섞여 있어 자동 분류가 어려움(제목 패턴으로 추정 분류가 가능한지는 실제 제목 표본을 봐야 판단 가능 — 이번 설계에서는 보류로 남김).

## 7. 스크립트 아키텍처 (제안)

PHP CLI 스크립트로 설계 — Rhymix의 `MemberController`/`DocumentController`/`FileController` 등 기존 컨트롤러 클래스를 그대로 호출하는 방식을 권장(직접 INSERT 쓰기보다 안전 — 캐시 무효화, 시퀀스 관리, 파생 컬럼 계산을 Rhymix가 알아서 처리).

```
scripts/migration/
├── 00_bootstrap.php          # Rhymix 부트스트랩 로드 + 레거시 DB 커넥션(별도 PDO)
├── 01_migrate_members.php    # xe_member -> rx_member (+그룹 매핑)
├── 02_migrate_boards.php     # 대상 게시판(notice/qna/adminboard)의 documents+comments
├── 03_migrate_files.php      # 02에서 이관된 문서에 딸린 첨부파일만 선별 이관
├── 04_verify.php             # 건수 대조, 깨진 참조(FK) 검사, 샘플 로그인 테스트 안내
└── config.php                 # 레거시 DB 접속정보, 대상 module_srl 매핑표
```

**실행 순서가 중요한 이유**: 회원이 먼저 있어야 문서의 `member_srl` 참조가 유효하고, 문서가 먼저 있어야 파일의 `upload_target_srl` 참조가 유효함.
