# 프론트엔드(Figma) ↔ 스킨 ↔ 백엔드 연결 구조

작성일: 2026-08-19
목적: 디자이너가 Figma로 스킨 디자인을 맡을 때, Rhymix(XE 계열)에서 디자인이 실제 화면으로 이어지는 구조를 이해하고 작업 범위를 나누기 위한 문서.

## 1. Rhymix 렌더링 구조 개요

Rhymix는 **"모듈(백엔드 로직)"과 "스킨(화면 템플릿)"이 분리**된 구조입니다. 실제 `kitel_web/xe/modules/board/` 폴더로 확인한 예시:

```
modules/board/
├── board.controller.php   # 쓰기·삭제 등 처리 로직 (백엔드)
├── board.model.php        # 목록 조회·데이터 가공 (백엔드)
├── board.view.php         # 어떤 데이터를 화면에 넘길지 준비 (백엔드)
└── skins/
    ├── default/            # 스킨 1
    │   ├── list.html        # 게시글 목록 템플릿
    │   ├── _read.html        # 게시글 상세 템플릿
    │   ├── write_form.html   # 글쓰기 폼 템플릿
    │   ├── comment_form.html
    │   ├── board.default.css
    │   ├── board.default.js
    │   └── skin.xml          # 스킨 메타정보(이름/작성자/썸네일 등)
    ├── sketchbook5/          # 스킨 2 (기존 사이트가 쓰던 것)
    └── xedition/             # 스킨 3
```

- **모듈(controller/model/view.php)**: "게시글 목록을 가져와라", "이 사용자가 이 글을 볼 권한이 있는가" 같은 로직. **백엔드 개발자 영역.**
- **스킨(list.html 등)**: 모듈이 준비한 데이터를 실제 HTML로 어떻게 그릴지. **디자이너의 Figma 결과물이 이 레이어로 변환됩니다.**
- 하나의 모듈(예: board)에 여러 스킨이 동시에 존재할 수 있고, 게시판마다 다른 스킨을 지정할 수 있습니다(예: Kitel News와 세미나 게시판이 다른 룩앤필을 가질 수 있음).

이 외에 **레이아웃(Layout)** 이라는 상위 개념이 하나 더 있습니다 — 헤더/푸터/GNB/사이드바처럼 **모든 페이지에 공통으로 씌워지는 틀**이며, `layouts/[레이아웃명]/layout.html` 하나로 관리됩니다. 스킨은 이 레이아웃 안의 "본문 영역"만 채웁니다.

```
방문자가 보는 화면 = 레이아웃(공통 헤더/푸터/GNB) 안에
                    └ 스킨(해당 게시판/모듈의 콘텐츠 영역)
```

## 2. 데이터가 화면으로 이어지는 흐름

1. 방문자가 게시판 URL 접속
2. **모듈(백엔드)**: 권한 확인 → DB 조회 → 데이터를 템플릿에서 쓸 변수로 준비(예: `$document_list`, `$list_config` 등)
3. **스킨 템플릿(list.html)**: 그 변수를 받아 HTML로 렌더링. 실제 코드 예시(`modules/board/skins/default/list.html`):

```html
<tbody cond="$document_list || $notice_list">
  <tr class="notice" loop="$notice_list=>$no,$document">
    ...
    {$document->getTitleText()}
    ...
  </tr>
</tbody>
```

`loop="..."`(반복문), `cond="..."`(조건 분기), `{$변수}`(값 출력) 같은 태그가 순수 HTML 안에 섞여 들어갑니다. **디자이너가 만든 정적 HTML/CSS를 이 형식으로 "퍼블리싱"하는 작업이 스킨 제작의 핵심**이며, 이 부분은 Figma만으로는 끝나지 않고 반드시 코딩(퍼블리싱) 단계가 필요합니다.

> 참고: 위 예시는 오래된 XE 문법 그대로이며(기존 사이트가 2013년경 스킨), Rhymix는 이 문법과 호환되면서 최신 문법도 일부 지원합니다. 정확한 최신 문법은 실제 Rhymix 개발환경에서 확인 필요.

## 3. 이번 프로젝트에서 화면을 세 그룹으로 나눠서 보는 게 좋습니다

### (A) 공통 레이아웃 — 헤더/푸터/GNB/사이드바
전 페이지 공통. Figma에서 이 부분은 "레이아웃"으로 명확히 분리해서 작업해주는 게 좋습니다. 로그인 상태/미로그인 상태에 따라 GNB 노출이 달라질 수 있는 부분(예: "임원진 전용" 메뉴)도 함께 고려 필요.

### (B) 표준 게시판형 화면 — Rhymix 스킨 규격으로 소화 가능
Kitel News, 세미나 게시판, 건의사항, 공유 게시판 등 "제목/목록/본문/글쓰기" 패턴을 벗어나지 않는 게시판들입니다. 이런 화면은 Rhymix 표준 스킨 세트(`list.html`, `_read.html`, `write_form.html`, `comment_form.html` 등)로 정확히 대응되므로, Figma에서도 **"목록 화면 / 상세 화면 / 글쓰기 화면"** 단위로 프레임을 나눠주시면 그대로 스킨 제작에 매핑됩니다.

몇몇 게시판은 표준 패턴에 상태(state) 분기가 추가로 필요합니다 — Figma 목업에도 함께 포함되면 좋습니다:
- **Kitel News**: 본문 잠금 상태(비로그인/미가입 회원이 봤을 때의 "로그인 후 확인 가능" 화면)
- **과제게시판**: 준회원 관점(제출 전/제출 완료), 정회원 관점(전체 열람)
- **건의사항**: 익명 표시 상태

### (C) 커스텀 화면 — 표준 스킨 틀을 벗어나는 것들
[board-feature-specs.md](board-feature-specs.md)에서 "Rhymix 구현 메모"에 커스텀 개발이 필요하다고 표시한 항목들:

- **캘린더** (월/주 뷰, 이벤트 등록)
- **과제게시판 제출현황 대시보드** (과제 × 준회원 매트릭스)
- **작품전시회 갤러리** (카드형 그리드, 승인 전/후 상태)
- **자료실 파일 브라우저** (폴더 트리 탐색)
- **기자재 대여 시스템** (이미 XE와 완전히 분리된 독립 앱)

이 화면들은 Rhymix의 "스킨" 규격(list.html 같은 정해진 템플릿 세트)에 들어맞지 않는, **사실상 처음부터 새로 만드는 화면**입니다. Figma에서 자유롭게 디자인하시면 되고, 이 부분은 스킨 매니페스트(skin.xml) 형식이 아니라 백엔드 개발자가 화면 전체를 코드로 직접 구현하는 방식이 될 가능성이 높습니다. (B)보다 디자이너-개발자 간 스펙 핏 확인이 더 필요한 영역입니다.

## 4. Figma 핸드오프 시 챙기면 좋은 것

- **컴포넌트/디자인 토큰 정리**: 색상, 타이포그래피, 버튼/폼 스타일 등을 공용 컴포넌트로 정리해두면 (B)/(C) 양쪽에 일관되게 적용하기 쉽습니다.
- **상태별 화면**: 빈 상태(글 없음), 로딩, 에러, 권한 없음/잠금 화면도 함께 준비되면 좋습니다 (특히 3-(B)에서 언급한 상태 분기들).
- **반응형 브레이크포인트**: 모바일 대응 필요 여부와 기준 폭.
- **(A)/(B)/(C) 구분을 프레임/페이지 단위로 미리 나눠서 작업**해주시면 개발 쪽에서 스킨 제작 범위와 커스텀 개발 범위를 바로 구분할 수 있습니다.

## 5. 퍼블리싱 범위 확정

**디자이너가 HTML/CSS 퍼블리싱까지 담당하기로 확정.** 디자이너가 정적 HTML/CSS를 넘기면, 개발 쪽은 그 마크업에 Rhymix 템플릿 태그(`loop`, `cond`, `{$변수}` 등)만 끼워 넣는 식으로 작업할 수 있어 (B) 표준 게시판 스킨(`list.html`/`_read.html`/`write_form.html`)과 (C) 커스텀 화면 모두 개발 쪽 부담이 크게 줄어듦.

다만 (C) 완전 커스텀 화면(캘린더, 과제 대시보드, 작품전시회 갤러리 상태 전이, 자료실 파일 브라우저)은 정적 마크업만으로는 끝나지 않고 **JS 상호작용(달력 네비게이션, 대시보드 필터, 파일 트리 탐색 등)** 이 필요한 부분이 있어, 디자이너의 퍼블리싱 결과물에 이 상호작용까지 포함되는지, 아니면 정적 마크업만 넘기고 상호작용은 개발 쪽이 이어받는지는 화면별로 착수 시점에 확인 필요.
