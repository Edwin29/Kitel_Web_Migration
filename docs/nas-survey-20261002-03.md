# KITEL 홈페이지와 NAS 조사 기록

기록일: 2026-10-03 KST. 2026-10-02 및 2026-10-03에 이 대화에서 수행한 읽기 전용 조사의 결과를 보존한다. 후속 작업은 [안정성 조사 계획](website-stability-investigation-plan.md)을 따른다.

현재 확인된 핵심은 홈페이지와 파일 서비스의 자원 공유, 분리된 회원 관리, PHP CPU 포화 징후다. RAM 부족을 모든 504의 확정 원인으로 취급하지 않는다. Drive 이관 방식, 서비스 분리, 장비 구매는 아직 확정하지 않았다.

## 조사 범위와 근거의 한계

- 사용자가 지정한 NAS에 SSH로 접속해 OS 통계, 프로세스, 설정, ACL, 제한된 디렉터리 목록과 로그를 읽었다. 운영 파일, ACL, 서비스 설정을 수정하거나 서비스를 재시작하지 않았다. 웹 부하 테스트도 하지 않았다.
- XE DB는 기존 설정으로 접속하되 `START TRANSACTION READ ONLY` 안에서 집계 SELECT를 실행하고 ROLLBACK했다. 10월 3일에는 DB 상태 및 프로세스 요약을 조회했다. 홈페이지 코어를 부팅하는 방식은 사용하지 않았다.
- Drive 및 Web Station SQLite는 `mode=ro&immutable=1`로 열었다. 보조 파일 생성을 피하지만 WAL의 미반영 변경은 포함하지 않으므로 완전한 최신 상태나 일관된 운영 백업으로 취급하지 않는다.
- 원시 로그와 개인별 계정 연결표를 repository에 저장하지 않았다. 이 문서는 도구 출력의 집계와 해석을 보존하며 원시 증거 전체의 사본은 아니다. 개인정보, 암호, 토큰, 파일 본문을 포함하지 않는다.
- SSH 계정에서 비밀번호 없는 sudo는 사용할 수 없었다. 현재 PHP-FPM 로그와 시스템 로그는 권한 때문에 읽지 못했다. OOM 발생 여부, 최신 느린 PHP 요청, 현재 Drive 공유 링크와 클라이언트 상태는 미확인이다.
- 조사용 SSH와 DB 접속은 서버의 통상적인 접속 기록을 발생시킬 수 있다. 운영 콘텐츠와 설정에 대한 변경 작업은 하지 않았다.

### 계정과 ACL

| 체계 | 관측 결과 |

| LDAP | 계정 158개. 정회원 64, 졸업생 73, 임원단 40명 등. 중복 소속 가능 |
| 아이디 비교 | 대소문자 정규화 후 일치 문자열 113, LDAP에만 45, 홈페이지에만 589 |
| 대여 권한 | 정회원=user, 관리그룹·기술부=admin |
| document | 졸업생에게도 변경·삭제를 포함한 ACL |
| 교육·공모전·KITEL 자료 | 졸업생은 읽기 중심 ACL |
| 임원단 | 정회원·졸업생의 읽기 ACL도 존재 |
| 공통 문제 | LDAP 그룹, DSM 개인 계정, 패키지 계정, 이름이 해석되지 않는 항목이 혼재 |

아이디 일치는 동일 인물 확인을 대신하지 않는다. 그룹 수 차이만으로 잘못된 계정이라고 단정하지 않는다. ACL은 Drive·Photos의 앱 권한 및 하위 예외를 포함한 최종 접근 테스트를 대신하지 않는다. 이름이 해석되지 않는 ACL을 바로 고아 계정으로 간주하거나 패키지 계정 권한을 일괄 삭제해서는 안 된다.

### Drive와 Archive

Drive의 디스크 메타데이터에서 document, 교육 자료, 대회 공모전, KITEL 관련 자료, 임원단 공유 경로와 개인 홈 경로 28개를 확인했다. photo는 이 표본에서 팀폴더 항목을 확인하지 못했다. metadata에 폴더별 버전 설정 차이가 있으나 현재 유효 정책은 Admin Console에서 확인해야 한다.

document 안에는 총회 자료, 제안서, 세미나, 멘토멘티, 불참사유서, 족보 등이 혼재한다. 공동 작업, 개인 파일, 교육 자료, 임원단 문서, 사진은 각각 다른 접근·보존 정책이 필요하다. Active Library / 읽기 전용 Legacy Archive / Drive 공동 편집 / 임원단 제한 영역 분리는 후보이며 확정 정책이 아니다.

현재 `custom_modules/archive`는 두 grant(list/manage), 웹 root 아래 파일 저장, GET 또는 POST 삭제, 하위 폴더의 즉시 재귀 삭제 구조다. 버전·휴지통·파일별 권한·활동 이력을 갖춘 Drive 대체재는 아니다. Phase 5 재개 전 보안과 변경·복구 정책을 정해야 한다. 코드는 수정하지 않았다.

access 표본 중 `/index.php` 2,941건, `search_target=tag` 2,528건, `act=IS` 1,135건, `search_keyword` 932건이었다. 검색·페이지·정렬 조건의 조합이 다수이며, 343개의 client 값이 관측됐다. 이 수치를 실제 이용자 수로 간주하지 않는다. 반복 탐색·자동 수집 기여 가능성은 있으나 악성 공격 여부는 확정하지 않았다.

해당 nginx service 설정은 Apache `127.0.0.1:915`로 전달하고 connect/read/send timeout이 각각 60초였다. FPM 설정에서 slowlog/status 지시어는 확인되지 않았다. 최신 PHP-FPM 및 OS 로그는 읽기 권한이 없어 확인하지 못했다. timeout 오류 표본, 200 위주의 접근 표본, 10월 3일 자원 표본은 서로 다른 시간 범위다. 이 자료로 특정 요청이 오늘 504를 만들었다고 단정하지 않는다.

## 기존 판단의 정정과 미결 가설

1. swap 잔량만으로 현재 RAM 고갈 또는 모든 504의 원인을 확정한 9월 문서의 설명은 과도하다. 가용 메모리와 swap 입출력, OOM, CPU·I/O를 함께 확인해야 한다.
2. 현재는 PHP CPU 포화와 처리 대기의 기여 가능성이 높다. 실제 요청 처리 시간, FPM queue, 코드 경로를 확인해야 인과관계를 좁힐 수 있다.
3. 설치된 패키지 수는 실행 부하와 같지 않다. Drive·Photos·백업의 동시 작업 영향은 시간 상관관계로 검증한다.
4. 기존 메일 조치는 9월의 발송·수신 기록이다. 이번에는 릴레이 파일의 존재·권한만 확인했으며 새 발송 테스트는 하지 않았다.
5. 웹·DB 분리 또는 새 NAS는 검토 후보다. 내부 개선의 효과를 평가하기 전에 현재 기기로 불가능하다고 확정하거나 구매 모델을 정하지 않는다.

## 재조사할 근거 위치

- OS: `/proc/stat`, `/proc/meminfo`, `/proc/vmstat`, 프로세스 통계, 디스크·부하 값.
- 웹: `/etc/nginx/sites-enabled/`, 해당 `.service.*.conf`, `/usr/local/etc/apache24/sites-enabled/`.
- PHP: `/usr/syno/etc/packages/WebStation/php_profile/5589cbe0-d35b-44d0-aabd-96f0645a9ab6/fpm.conf`.
- 로그: `/var/packages/WebStation/var/log/` 및 `/var/packages/PHP7.4/var/log/php74-fpm.log`, `/var/log/messages`.
- Drive: `/var/packages/SynologyDrive/etc/`의 설정과 읽기 전용 metadata. 내부 DB 스키마를 운영 연동 API로 사용하지 않는다.
- 권한: 공유 root와 대표 하위 폴더의 `synoacltool -get`, LDAP 그룹 집계, XE 그룹과 대여 권한 집계.
