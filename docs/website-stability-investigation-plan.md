# KITEL 홈페이지 과부하 개선 조사 계획

작성일: 2026-10-03 KST. 상태: 계획 수립 후 사용자 승인으로 읽기 전용 탐색 시작. Phase 11과 Archive 구현은 보류한다. [기존 조사 기록](nas-survey-20261002-03.md)을 출발점으로, 현재 장비의 설정·코드 개선으로 안정화할 수 있는지와 서비스 분리·NAS 교체가 필요한 조건을 판단한다.

사용자는 계획이 준비되면 탐색을 시작하고 근거에 따라 계획을 조정하도록 허용했다. 복구 불가능하거나 서비스에 급격한 영향을 끼치는 행동은 금지했다. 현재는 기존 읽기 전용 조사 범위에서 진행한다. 운영 변경이 필요하면 대상·영향·복구 방법을 먼저 구체화하고 기존 읽기 전용 범위를 넘어서는 변경은 별도 승인을 받는다. 지속 수집이나 운영 부하 재현을 탐색 승인에 포함된 것으로 간주하지 않는다. 계획 변경 이유와 조사 결과는 문서에 남긴다.

## 답해야 할 질문

1. 반복되는 504는 어떤 요청에서 시작하며 CPU, PHP 대기, DB, 메모리, 디스크, 네트워크 중 어디에서 지연되는가?
2. 현재 XE의 문제와 신규 Rhymix에서도 남을 구조적 문제는 각각 무엇인가?
3. 설정·코드·운영 스케줄 개선으로 필요한 처리량과 복구성을 확보할 수 있는가?
4. Drive를 유지하면서 홈페이지·DB를 분리하면 어떤 장애 의존성이 사라지고 무엇이 남는가?
5. 새 NAS 또는 별도 웹 장비가 필요하다면, 어떤 측정 근거로 CPU·RAM·저장소·지원 수명을 선택할 것인가?

현재 PHP CPU 포화는 관측 사실이다. 모든 504의 단일 원인, Drive의 주원인 여부, RAM 증설 또는 NAS 교체만으로 해결되는지는 미확정이다.

2026-10-03 1차 탐색에서 동일 FPM 설정의 OPcache 미적재, XE 객체 캐시 설정 부재, 주요 XE 테이블의 MyISAM 사용과 key_buffer_size=16KiB를 확인했다. 이에 따라 장비 선정 전에 캐시·PHP·검색 처리 비용의 검증을 우선한다. [서비스 배치](website-stability/service-map.md)와 [1차 발견사항](website-stability/findings.md)에 확인 범위와 한계를 기록했다.

## 조사 단계

| 단계 | 조사 내용 | 산출물 | 다음 단계로 넘어갈 조건 |
|---|---|---|---|
| 1 서비스 구조 확정 | 홈페이지·대여·Drive·Photos·LDAP·DB·백업의 프로세스, 저장소, 인증, 통신 및 장애 의존성 확인 | 서비스 배치도와 미확인 항목 | 각 서비스의 실행 위치·책임·의존성이 연결됨 |
| 2 장애 기준선 확보 | 실제 504와 동일 시간대의 요청·자원·PHP·DB 기록을 연결 | 장애별 타임라인과 정상 시간대 비교 | 최소 한 번의 실제 장애를 연결하거나 재현 실패와 관측 한계를 명시 |
| 3 코드와 설정 원인 분류 | 검색·페이지 조합·반복 계산·캐시·DB·파일 다운로드·외부 호출·PHP pool 분석 | 원인 후보별 근거·반증·최소 개선안 | 후보별 병목 지점과 검증 방법이 구체화됨 |
| 4 내부 개선 효과 검증 | 승인된 변경을 한 종류씩 비교. 동일 요청 구성·데이터·부하 기준 사용 | 개선 전후 결과와 회귀·롤백 결과 | 처리량·지연 개선이 관측되고 권한·기능 회귀가 없음 |
| 5 배치와 장비 비교 | 현재 NAS 유지, 서비스 분리, NAS 교체의 비용·용량·복구성 비교 | 선택지별 근거와 예산안 | 성능 여유·운영 부담·복구 목표를 만족하는 후보 식별 |
| 6 실행 범위 확정 | 우선 수정 항목, 구매 여부, 이관 순서, 운영 담당 및 되돌리기 정리 | 실행 계획과 사용자 결정 사항 | 사용자가 변경 범위·예산·중단 시간을 결정 |

각 단계에서 확인된 사실과 추정을 구분해 `docs/website-stability/` 아래에 기록할 예정이다. 제안 파일은 `service-map.md`, `baseline.md`, `findings.md`, `experiment-results.md`, `options-and-budget.md`, `decision.md`다. 이 경로들은 향후 산출물이며 아직 조사 결과가 있는 것처럼 빈 완료 문서를 만들지 않는다.

## 장애 측정 방법

### 기록할 내용

- 사용자 관측 시각, URL의 기능 분류, 로그인 상태, 오류 또는 지연. 실제 비밀번호·세션·검색어·본문은 기록하지 않는다.
- 요청량과 상태 코드, 응답 시간 p50/p95/p99, nginx의 upstream 연결·응답 시간. 시간대와 표본 수를 함께 기록한다.
- CPU 실행·대기, 가용 RAM, swap 입출력, OOM, 디스크 대기·지연·여유 공간.
- PHP 활성/유휴 워커, listen queue, max_children 도달, 느린 요청의 실행 위치, OPcache 실효 설정.
- DB 실행 수·잠금·느린 쿼리·테이블 엔진·인덱스와 캐시. buffer pool 16MiB만 보고 임의로 늘리지 않는다.
- 같은 시간의 Drive 동기화, 사진 처리, 인덱싱, 백업 작업. 설치 여부로 부하를 추정하지 않는다.

### 관측 범위와 수집 비용

우선 기존 로그로 장애를 연결한다. 부족하면 관리자 권한이 필요한 로그를 제한적으로 제공받거나 승인된 읽기 권한으로 조회한다. 진단을 위해 계정의 권한을 영구 확대하는 방식을 기본으로 삼지 않는다.

지속 관측이 필요하면 보통 사용과 피크·정기 작업을 포함하는 24~72시간을 초안으로 잡고, 실제 주간 작업이 빠지면 필요한 구간만 추가한다. 최초에는 30~60초 단위의 가벼운 통계로 시작하고, 장애 구간에만 짧은 세부 표본을 사용한다. 수집 자체의 CPU·디스크 사용, 로그 용량·보존 기간과 종료 방법도 함께 정한다.

현재 20초 표본과 과거 로그는 기준선의 일부일 뿐이다. 로그 시각이 맞지 않거나 한 번도 504를 포착하지 못한 경우 원인 확정으로 단계 종료하지 않는다. 필요한 추가 관측을 명시한다. 이번 단계에서 예약 실행이나 백그라운드 수집기를 설치하지 않는다.

## 우선 검증할 가설

| 가설 | 현재 근거 | 추가로 필요한 증거 | 결과에 따른 개선 후보 |
|---|---|---|---|
| 검색·정렬 URL 조합의 반복 접근 | 과거 access 표본의 검색·페이지 조합 | 현재 요청 분포, 수집 주체, 요청별 비용 | 입력 조합 제한·정규 URL·공개 캐시·과도한 요청 제어 |
| PHP 코드가 CPU를 오래 점유 | 10월 3일 PHP CPU·실행 대기 | 느린 요청 trace, 캐시 hit, 주요 함수 비용 | 반복 처리 제거, 캐시, 호환되는 PHP 환경 개선 |
| PHP 처리 대기열이 누적 | child 12개와 max_children=12 | 실제 queue, 요청 시간, busy worker | 측정에 맞춘 동시성·요청 제한·오래 걸리는 작업 분리 |
| RAM 또는 I/O 압박 | 작은 RAM과 서비스 공유 | 장애 시점 swap 입출력·OOM·디스크 지연 | 서비스·스케줄 조정, 메모리 또는 저장소 증설·분리 |
| DB 조회·잠금 병목 | 웹 요청은 DB에 의존, slow log 미활성 | 실행 계획·엔진·잠금·느린 조회 | 쿼리·인덱스·DB 설정 개선 |
| Drive·백업과 홈페이지가 경쟁 | 동일 NAS에서 서비스 운영 | 작업별 자원과 504의 시간 상관관계 | 인덱싱 범위·작업 시간·자원 배치 조정 |
| 외부 호출·세션 등에서 대기 | 아직 직접 증거 없음 | 느린 요청의 대기 위치 | 외부 호출 timeout·실패 처리·세션 점유 개선 |

timeout 연장, worker 증설, swap 설정 변경, 패키지 일괄 삭제를 첫 처방으로 삼지 않는다. robots.txt는 협조하는 crawler 안내이며 강제 접근 제한을 대체하지 않는다. 학교 공용 IP와 정상 회원 사용을 고려해 제한 단위를 설계한다. 비공개·회원별 콘텐츠는 공용 캐시에 섞지 않는다.

## 내부 개선 실험

먼저 정적 분석과 로컬 또는 격리된 검증 환경에서 확인한다. 운영 데이터 사용 시 필요한 최소 범위만 비식별화하고 별도 보관한다. 운영 NAS에 승인 없는 동시 요청이나 부하 테스트를 보내지 않는다.

각 실험에는 원인 가설, 변경 파일·설정, 대상 환경, 기존 값, 기대 효과, 측정 지표, 기능·권한 검사, 실패 조건과 복구 절차를 붙인다. 동시 변경으로 효과를 구분할 수 없게 만들지 않는다. 운영 확인이 필요하면 사용자가 승인한 범위와 시간에서 적용한다.

현재 XE 개선과 신규 Rhymix 검증은 별도로 기록한다. 새 코드가 자동으로 더 빠르다고 가정하지 않는다. 초기·워밍업 후 캐시, 대표 데이터 규모, 회원/비회원, 검색·목록·상세·첨부·대여, 동시 요청을 비교한다. 파일 크기와 다운로드 시간은 일반 HTML 응답 시간에서 분리한다.

수용 기준 초안은 정상 이용의 HTML p95 2초 이하·p99 5초 이하, 관측 구간 서버 5xx 비율 0.1% 미만, 대표 기능 QA 중 504 없음이다. 현재 측정된 성능이나 확정 SLA가 아니며 단계 2에서 정상 요청 범위와 함께 조정한다. 짧은 테스트만으로 월간 가용성을 입증하지 않는다. 실측 정상 피크와 추가 여유 부하에서 queue가 계속 늘지 않고, 부하가 줄면 회복되는지도 확인한다.

## 장비와 서비스 배치 비교

| 후보 | 검토 범위 | 채택 근거 | 한계 |
|---|---|---|---|
| A 현재 NAS 유지 | 코드·캐시·요청 제어·스케줄·설정 개선 | 정상 피크와 여유 부하에서 목표 충족 | 장애 영향 범위와 하드웨어 여유 제약은 남음 |
| B 현재 NAS 내부 서비스 정리 | 필요한 서비스·인덱싱·작업 배치 조정 | 충돌 작업이 주요 원인이며 기능 유지 가능 | 같은 장비 내 분리는 물리 CPU·RAM을 늘리지 않음 |
| C 새 NAS로 교체 | 웹·Drive 유지 가능 모델과 지원 기간 검토 | 개선 후에도 자원 부족, 파일 서비스도 증설 필요 | 동일 장비 집중, 이관·복구·패키지 호환 비용 |
| D 웹과 DB를 별도 환경으로 이동 | 기존 NAS는 Drive·사진·대용량 보관 | 웹 처리·보안 업데이트·장애 분리가 주요 목표 | 별도 운영 비용, NAS 접근과 인증 연결 설계 필요 |
| E 단계적 병행 | 웹 분리 후 NAS는 수명·파일 수요 기준 교체 | 두 서비스의 교체 시점과 요구가 다름 | 일시적인 두 환경 관리와 이관 비용 |

웹만 이동하고 DB를 NAS에 남기는 배치의 장애 의존성도 비교한다. NAS가 잠시 응답하지 않아도 기본 홈페이지와 로그인은 가능한지 검증한다. 홈페이지 계정에 NAS 전체 공유폴더 권한을 부여하는 방식은 사용하지 않는다. 권한을 확인한 파일 전달과 필요한 저장소만 연결하는 구조를 검토한다.

단계 5에서 당시 판매·지원 정보를 공식 자료로 확인한다. 특정 모델·RAM 용량을 지금 확정하지 않는다. CPU는 코어 수뿐 아니라 실제 PHP 처리 성능, RAM은 OS·DB·파일 서비스·동시 worker의 실제 사용과 여유, 저장소는 지연·용량·버전·백업 증가량으로 산정한다. 기존 드라이브 재사용, 아키텍처와 패키지 호환, UPS, 복구 가능한 독립 백업도 포함한다.

비용은 초기 장비·디스크·UPS·이관 비용과 3년간 호스팅·전력·백업·운영 부담으로 비교한다. 예산 상한과 허용 중단 시간은 후보별 요구가 나온 뒤 사용자에게 확인한다. 성능 개선만으로 보안 업데이트·복구성·담당자 인수인계 문제를 해결했다고 판단하지 않는다.

## 권한과 자료실 변경의 연결 범위

회원 상태·부서·서비스 권한을 한 화면에서 관리하는 방향은 유지한다. 단일 관리 화면, 로그인 통합, 물리 서버 통합은 서로 다른 설계다. 웹·DB를 분리해도 중앙 관리가 가능하도록 계정 연결과 권한 반영 경로를 설계한다.

Drive 이관은 성능 문제를 해결한다는 이유로 전체 복사를 먼저 하지 않는다. 공동 편집·동기화, Active Library, Legacy Archive, 임원단 문서, Photos별 사용량과 필수 기능을 확인한다. `custom_modules/archive`는 재개 전에 보안·삭제·버전 정책을 보강해야 하며 이 조사에서 구현하지 않는다.

## 최종 판단에 필요한 결과

- 관측된 장애의 원인과 아직 미확인인 원인을 명시한 근거표.
- 홈페이지에서 실제 수정할 항목과 파일·설정 위치, 기대 효과, 검증·복구 방법.
- 현재 장비 유지가 가능한 조건 및 교체·분리가 필요한 측정 근거.
- 후보별 예산·운영 부담·장애 영향·백업과 복구 비교.
- 다음 실행 범위와 사용자 결정 사항. 구매나 운영 변경은 이 결과를 검토한 뒤 진행한다.

문서만으로 장비 교체의 필요성을 확정하거나, 낮은 트래픽의 한 번 성공을 안정화 완료로 선언하지 않는다. Phase 11 재개는 이 조사와 별도 지시로 결정한다.
