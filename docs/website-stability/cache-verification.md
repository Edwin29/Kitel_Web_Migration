# 홈페이지 캐시의 검증 후보

2026-10-03 추가 조사. 운영 변경 없이 코드·설정·파일 메타데이터를 읽어 다음 실험을 구체화했다. [추가 관측](baseline.md)과 [1차 발견사항](findings.md)을 함께 읽는다. 현재 대상은 기존 운영 XE이며 신규 Rhymix에 같은 설정을 그대로 이식하는 계획이 아니다.

## PHP OPcache

기존 확인대로 동일 바이너리·ini·scan directory를 사용한 별도 모듈 목록 프로세스에서는 OPcache가 적재되지 않았다. 이번 운영 프로세스 maps 조회는 권한 때문에 실패해 실효 상태를 추가 확정하지 못했다. 관리 화면 또는 승인된 운영 진단에서 해당 pool의 적재 상태를 먼저 확인한다. 공개 phpinfo 페이지는 만들지 않는다.

격리 검증은 운영과 호환되는 PHP·XE 복제 환경에서 수행한다. NAS의 ARM 장비와 다른 CPU에서 나온 절대 처리량을 운영 처리량으로 간주하지 않는다. 같은 검증 장비 안에서 변경 전후의 상대 효과를 비교한다.

- 변경 후보: 해당 PHP 프로필에 OPcache 확장을 올바르게 적재하고 갱신 검사를 유지.
- 측정: 동일 페이지 구성에서 워밍업 전후 CPU/요청, 응답 시간, 메모리, 캐시 적중·용량 상태.
- 회귀: 로그인·권한, 글 작성·수정, 파일 캐시 갱신, 배포 직후 코드 변경 반영.
- 중단 기준: 오류 증가, 오래된 코드/설정 노출, 메모리 부족 또는 개선 없이 운영 부담만 증가.
- 운영 적용 전 필요 사항: 지원되는 Web Station 설정 경로, 기존 값 백업, pool 재적용 영향, 원복 절차. 이번 조사에서는 수행하지 않음.

## XE 객체 캐시를 정확히 구분하기

`use_object_cache` 미설정은 모든 객체 재사용이 꺼졌다는 뜻이 아니다. 운영과 SHA256이 일치하는 `module.model.php`에서 메뉴에 연결되는 모듈 정보·사이트·설정·트리거 등은 `CacheHandler::getInstance('object', null, true)`를 사용했다. 선택형 설정이 없어도 file handler로 내려가는 경로다.

운영 `files/cache/store`에서 최대 2,000개 파일의 메타데이터만 확인했다. 2,000개 상한에 도달했으며 표본 중 1개는 당일 갱신돼 있었다. 전체 파일 수나 실제 적중률은 측정하지 않았고, 캐시 내용도 읽지 않았다. 파일 캐시가 존재하고 갱신되는 증거와 요청별 사용 효과는 구분한다.

따라서 앞선 쉬운 설명의 ‘메뉴·설정을 매번 DB에서 다시 가져온다’는 예를 현재 사이트 전체에 적용하면 부정확하다. 개선 범위는 이미 동작하는 file cache와 선택형 객체 캐시에 의존하는 경로를 나누어 측정해야 한다.

### 방문 통계에서 확인한 구체적인 차이

운영의 PC/mobile 활성 애드온 캐시에 counter 참조가 있었고 counter 소스 3개가 로컬 사본과 일치했다.

- `counterModel::isLogged()`는 선택형 객체 캐시를 요청한다. 사용할 수 없으면 해당 일자의 IP 방문 여부를 DB에서 조회하는 경로로 진행한다.
- `isInsertedTodayStatus()`는 file fallback을 허용하므로 선택형 캐시 미설정과 동작이 다르다.
- `counterExecute()`는 방문 상태에 따라 페이지뷰 UPDATE 또는 방문 로그 INSERT·집계를 수행한다. 읽기 캐시가 이 쓰기 작업을 모두 없애주지는 않는다.

이 경로는 검증할 후보이며 주요 병목이라는 측정 결과는 아니다. 방문 통계 기능을 끄거나 과거 로그를 삭제하지 않았다.

### 검증 방향

먼저 선택형 캐시 미설정과 file 선택을 격리 환경에서 비교하고, 실제 조회 감소·추가 파일 쓰기·파일 증가·정합성을 측정한다. 효과가 부족하고 공용 메모리 캐시가 필요할 때만 별도 서비스 운영 비용을 비교한다. PHP의 memcached 확장이 존재하는 것과 캐시 서버가 준비된 것은 다르다.

CacheMemcache의 `isSupport()`는 실제 set 동작을 하고, CacheFile 생성자와 읽기 경로 일부도 디렉터리 생성·오래된 파일 삭제를 수행한다. 이번 읽기 전용 조사에서는 handler를 직접 실행하거나 지원 확인 메서드를 호출하지 않았다.

방문 통계 정확성, 날짜 경계, 로그인·로그아웃, 메뉴·권한 변경 직후 갱신을 회귀 대상으로 둔다. 회원별 비공개 콘텐츠의 공용 페이지 캐시는 이번 후보에 포함하지 않는다.

## MyISAM 인덱스 캐시

key_buffer_size=16KiB와 캐시 바깥 읽기 약 21.6%가 재관측됐다. 홈페이지 DB의 MyISAM 인덱스 전체 메타데이터 합계는 약 24.5MiB다. 운영 메모리 여유와 실제 사용 범위를 확인한 뒤 검증 환경에서 작은 단계로 용량을 비교한다. 전체 인덱스 크기를 그대로 최적 용량으로 정하지 않는다.

같은 데이터·요청 구성과 충분한 워밍업 조건에서 CPU, 응답 시간, Key_reads/Key_read_requests, 잠금 대기, 메모리·swap 입출력을 비교한다. 서버 전체 통계를 사용하면 다른 DB 작업도 동일하게 통제하거나 별도 기록한다. 캐시 적중률 개선만으로 사용자 응답 개선을 선언하지 않는다.

다른 캐시와 동시에 바꾸거나 MyISAM→InnoDB 변환·인덱스 추가·테이블 정리를 함께 수행하지 않는다. 운영 적용은 설정 지속 방식과 되돌릴 기존 값을 확정한 뒤 별도 승인한다.

## 실험 순서와 완료 기준

| 순서 | 작업 | 완료 근거 |
|---|---|---|
| 1 | 최신 로그 가시성 및 운영 pool 상태 확인 | 현재 요청·오류·설정의 증거 확보. 접근 불가 항목은 유지 |
| 2 | 격리 환경 기준선 마련 | 버전·데이터 범위·요청 구성·장비 차이를 기록 |
| 3 | OPcache만 비교 | CPU·지연·갱신 회귀 결과 |
| 4 | MyISAM 캐시만 비교 | 응답 개선과 메모리 영향, 다른 DB 영향 |
| 5 | XE 선택형 캐시 비교 | 실제 조회 감소와 추가 쓰기 비용, 정합성 |
| 6 | 유효한 개선 조합 비교 | 조합 효과와 피크 후 회복. 운영 적용 후보·복구 절차 작성 |

순서는 새 근거에 따라 바꿀 수 있다. 격리 환경 구축·부하 실험은 아직 수행하지 않았다. 내부 개선 후에도 CPU 여유·지원 수명·복구성이 부족하면 웹·DB 분리와 NAS 교체 비교로 이어진다.
